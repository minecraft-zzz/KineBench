# VideoX HTTP Service Interface

This document describes the local HTTP interface that a VideoX service must provide so KineBench can call it during evaluation.

## Overview

KineBench can use a local VideoX service as its video generator through:

```yaml
generation:
  kind: http
  endpoint: http://127.0.0.1:8008/generate
  timeout_sec: 1800
  target_frames: 49
  size: [384, 384]
  extra_payload: {}
```

At runtime, KineBench does:

1. Reset the ManiSkill environment.
2. Render the first frame.
3. Build the task prompt.
4. Send `prompt`, `first_frame`, and generation parameters to the VideoX HTTP service.
5. Receive an mp4 path, URL, or base64 video from the service.
6. Read the returned video and continue with FoundationPose, gripper prediction, and ManiSkill rollout.

The existing ready-to-use config is:

```bash
configs/eval/maniskill_videox_http.yaml
```

## Required Endpoint

The service should expose:

```http
POST /generate
Content-Type: application/json
```

Default KineBench endpoint:

```text
http://127.0.0.1:8008/generate
```

You can change it in yaml:

```yaml
generation:
  kind: http
  endpoint: http://127.0.0.1:8008/generate
```

## Request JSON

KineBench sends the following JSON body:

```json
{
  "prompt": "Task prompt text...",
  "negative_prompt": "camera movement, ...",
  "seed": 43,
  "first_frame": "data:image/png;base64,...",
  "target_frames": 49,
  "num_frames": 49,
  "size": [384, 384],
  "output_size": [384, 384]
}
```

### Field Meanings

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `prompt` | string | yes | Full task prompt generated by KineBench. For fruit tasks, this already includes the selected fruit or fruit order. |
| `negative_prompt` | string or null | no | Negative prompt from KineBench. The service may ignore it. |
| `seed` | int or null | no | Generation seed. KineBench changes it across episodes/rollouts. |
| `first_frame` | string | yes | PNG image encoded as a data URI: `data:image/png;base64,...`. |
| `target_frames` | int | yes | Number of frames KineBench expects after loading the returned video. |
| `num_frames` | int | yes | Alias of `target_frames`, provided for VideoX-style APIs. |
| `size` | `[width, height]` | yes | Output/read size expected by KineBench. Usually `[384, 384]`. |
| `output_size` | `[width, height]` | yes | Alias of `size`. |
| `ref_video` | string | optional | Included only if `generation.ref_video` is set in yaml. |

Any values under yaml `generation.extra_payload` are merged into this request body after the default fields.

Example:

```yaml
generation:
  kind: http
  endpoint: http://127.0.0.1:8008/generate
  extra_payload:
    model_path: /path/to/videox/checkpoint
    guidance_scale: 5.0
```

The service will receive `model_path` and `guidance_scale` in the same JSON body.

## Response JSON

The service must return JSON with one of the following fields.

### Option A: Local Video Path

Recommended when VideoX and KineBench run on the same machine.

```json
{
  "video_path": "/zzz_new/projects/KineBench/tmp/videox_outputs/sample.mp4"
}
```

Aliases also accepted:

```json
{
  "path": "/path/to/video.mp4"
}
```

```json
{
  "output_path": "/path/to/video.mp4"
}
```

Requirement: the returned path must be readable by the KineBench process.

### Option B: Video URL

Useful if the VideoX service stores outputs behind a file server.

```json
{
  "video_url": "http://127.0.0.1:8008/files/sample.mp4"
}
```

Alias also accepted:

```json
{
  "url": "http://127.0.0.1:8008/files/sample.mp4"
}
```

KineBench will download the mp4 into the current episode attempt directory.

### Option C: Base64 Video

Works, but is not recommended for large videos.

```json
{
  "video_base64": "AAAA..."
}
```

Alias also accepted:

```json
{
  "video": "AAAA..."
}
```

The value may also be a data URI, for example:

```json
{
  "video_base64": "data:video/mp4;base64,AAAA..."
}
```

## Video Requirements

The returned video should be an RGB mp4 readable by `imageio`.

Recommended:

- Format: `.mp4`
- Frames: at least `target_frames` frames if possible
- Resolution: can be any reasonable resolution, but `[384, 384]` is preferred
- Camera: should remain static and match the first frame
- Robot: should preserve the first-frame robot appearance

KineBench will load the video and convert it to:

```text
[B, 3, T, H, W], float32, range [0, 1]
```

If the returned video has fewer than `target_frames`, KineBench pads by repeating the last frame. If it has more frames, KineBench samples frames according to the configured `generation.sampling` value:

```yaml
generation:
  sampling: uniform  # default
```

or:

```yaml
generation:
  sampling: head
```

## Minimal FastAPI Example

This is only an interface skeleton. Replace `run_videox(...)` with your actual VideoX generation call.

```python
from __future__ import annotations

import base64
import uuid
from pathlib import Path

from fastapi import FastAPI
from pydantic import BaseModel


app = FastAPI()
OUT_DIR = Path("/zzz_new/projects/KineBench/tmp/videox_http_outputs")
OUT_DIR.mkdir(parents=True, exist_ok=True)


class GenerateRequest(BaseModel):
    prompt: str
    negative_prompt: str | None = None
    seed: int | None = None
    first_frame: str
    target_frames: int = 49
    num_frames: int = 49
    size: list[int] = [384, 384]
    output_size: list[int] = [384, 384]


def save_first_frame(first_frame_data_uri: str, path: Path) -> None:
    payload = first_frame_data_uri.split(",", 1)[1]
    path.write_bytes(base64.b64decode(payload))


def run_videox(req: GenerateRequest, first_frame_path: Path, output_path: Path) -> None:
    # Replace this with your VideoX command or Python API call.
    # It should write an mp4 to output_path.
    raise NotImplementedError


@app.post("/generate")
def generate(req: GenerateRequest):
    stem = f"seed{req.seed if req.seed is not None else 'none'}_{uuid.uuid4().hex[:8]}"
    first_frame_path = OUT_DIR / f"{stem}_first_frame.png"
    output_path = OUT_DIR / f"{stem}.mp4"

    save_first_frame(req.first_frame, first_frame_path)
    run_videox(req, first_frame_path, output_path)

    return {"video_path": str(output_path)}
```

Run the service:

```bash
uvicorn videox_http_service:app --host 127.0.0.1 --port 8008
```

## Output Locations

KineBench writes results to:

```text
outputs/videox_http_eval_{timestamp}/{env_id}/{episode_id}/
```

Useful files:

```text
info.json
rollout.mp4
trajectory.h5
attempt_000/
attempt_001/
attempt_002/
```

The HTTP generator records the returned source video path in `info.json` under each rollout entry:

```json
{
  "generated_source": "/path/to/video.mp4"
}
```

## Error Handling

KineBench expects:

- HTTP status code `200` for successful generation.
- A JSON response containing `video_path`, `video_url`, or `video_base64`.
- The returned mp4 must exist and be readable.

If the service returns an error status, KineBench raises the HTTP error and stops the episode.

If the service returns a missing path, KineBench raises:

```text
FileNotFoundError: HTTP generator returned video_path, but file does not exist
```

If the response has no usable video field, KineBench raises:

```text
RuntimeError: HTTP generator response must include video_path, video_url, or video_base64
```

## Checklist For VideoX Service

- Accept `POST /generate`.
- Decode `first_frame` from `data:image/png;base64,...`.
- Use `prompt` directly; it already includes dynamic task details such as fruit type/order.
- Respect `seed` when possible.
- Generate a video with a static camera and robot appearance matching the first frame.
- Save an mp4 to a path readable by KineBench.
- Return `{"video_path": "/absolute/path/to/output.mp4"}`.
